## 1. 文档体系与分工

四类内容必须写在各自的位置，禁止串位：

| 载体 | 写什么 | 不写什么 |
|---|---|---|
| PRD | 产品行为、界面规则、限值、异常话术 | 技术实现、框架选型 |
| ARCHITECTURE.md | 结构、决策、约束、部署、横切规范 | 字段级接口细节、逐行代码说明 |
| API.md / openapi.yaml | 协议契约、字段、错误码、示例 | 内部实现、算法细节 |
| CONVENTIONS.md（本文） | 编码、注释、提交、评审规则 | 业务语义 |
| 代码注释 | 本段代码的意图、非显然的取舍、对文档章节的引用 | 标准与约定本身的定义、产品规则复述 |

判定口诀：**能被两个以上模块引用的规则写文档；只对一处代码有意义的解释写注释。**

## 2. 注释规范

### 2.1 基本形态

| 编号 | 规则 | 级别 |
|---|---|---|
| C-01 | 代码注释一律使用块注释 `/* ... */`，禁止 `//` 行注释与行尾注释 | 必须 |
| C-02 | 每段连续代码**之前**必须有且只有一段块注释，说明这段代码的意图 | 必须 |
| C-03 | 一段注释覆盖的连续代码不超过 **15 行**（含空行与括号行）；超出必须拆段并补充注释 | 必须 |
| C-04 | 注释语言为中文；标识符、协议字段、标准名称保留英文原文 | 必须 |
| C-05 | 注释描述「为什么这样做」与「有什么约束」，不复述代码字面含义 | 必须 |
| C-06 | 注释中可以且应当引用文档章节，格式见 2.3 | 应当 |
| C-07 | 禁止把接口字段说明、产品规则、错误码表搬进注释，改为引用文档 | 必须 |
| C-08 | 禁止保留被注释掉的旧代码；删除即删除，历史交给 Git | 必须 |
| C-09 | 禁止 `TODO` 无责任人、无上下文的写法；必须写成 `@todo(#issue) 说明` | 必须 |
| C-10 | 生成代码、第三方代码、`//go:build`、`//go:generate` 等编译器指令不受 C-01 约束（指令不是注释） | 例外 |

**与 Go 官方约定的关系**：Go 的 `go/doc` 同时解析 `//` 与 `/* */` 两种文档注释（出处：<https://go.dev/doc/comment>），因此 C-01 不与工具链冲突；`gofmt` 不会重排块注释内容，故块注释内部需自行保持对齐。

### 2.2 段落注释的写法

一段注释必须能回答至少两个问题：这段代码**要达成什么**、**受什么约束**。推荐结构：

```go
/*
 * 校验并扣减当日额度。
 *
 * 约束：扣减与任务创建必须在同一事务内完成，否则失败返还时会出现负数余额。
 * 幂等：同一任务只允许一条 CHARGE 流水，由 quota_ledger 的唯一索引兜底。
 * 参考：docs/ARCHITECTURE.md#88-额度与容量、docs/API.md#62-资源与校验
 */
```

禁止的写法：

```go
/*
 * 调用 Charge。
 */
```

原因：只翻译了函数名，没有提供任何代码之外的信息。

### 2.3 注释标签

| 标签 | 用途 | 示例 |
|---|---|---|
| `@doc` | 引用规范或设计文档章节 | `@doc docs/ARCHITECTURE.md#63-保存与冲突裁决` |
| `@see` | 引用相邻实现或对端代码 | `@see internal/domain/service/quota.go` |
| `@risk` | 标注已知风险与触发条件 | `@risk 供应商限流时任务会重排队，需监控队列深度` |
| `@todo(#123)` | 待办，必须带 issue 编号 | `@todo(#42) 补充 HEIC 服务端兜底解码` |
| `@invariant` | 不变量，修改此处必须同时满足 | `@invariant note.revision 单调递增且不跳号` |

标签必须出现在块注释内，格式为 `标签 内容`，一行一个，紧跟在描述段之后。

### 2.4 段落切分口径

15 行的计量口径：从块注释下一行起算，到下一个块注释前一行止，空行与仅含 `}` 的行计入。以下情形必须切段：

1. 一段逻辑中出现两个以上职责（校验 → 写入 → 发消息）；
2. 出现嵌套超过两层的分支；
3. 出现事务开始 / 提交这类边界；
4. 出现外部调用（数据库、对象存储、AI、邮件）。

### 2.5 包与导出标识符注释

- 每个包必须有包注释，紧贴 `package` 声明且中间无空行（出处：<https://go.dev/wiki/CodeReviewComments#package-comments>），同样使用块注释。
- 所有导出类型、函数、方法、常量必须有文档注释，说明用途、参数约束、返回值与错误语义；首个句子以被注释对象的名字开头（出处：<https://go.dev/doc/comment>）。
- 未导出但非平凡的类型与函数同样需要段落注释。
- 错误返回值必须写明可能的领域错误码，并指向 [API.md](API.md) 第 6 章对应条目。

### 2.6 注释与文档的引用格式

- 引用本文档体系内的文件使用相对路径：`docs/API.md`、`docs/ARCHITECTURE.md`。
- 引用章节使用 GitHub 风格锚点：`docs/ARCHITECTURE.md#82-错误模型`。
- 引用外部标准使用完整链接，例如 `RFC 9457 <https://www.rfc-editor.org/rfc/rfc9457.html>`。
- 禁止在注释中复制标准原文超过 3 行；需要展开时引用链接。

## 3. 代码规范

### 3.1 通用

| 编号 | 规则 |
|---|---|
| G-01 | 必须通过 `gofmt` 与 `goimports`；提交前本地执行，CI 阻断未格式化代码 |
| G-02 | 包名小写单词，不用下划线；文件名小写下划线 |
| G-03 | 接口在使用方定义（`application/port`），实现方不得反向定义接口 |
| G-04 | 所有跨进程调用必须接收并传递 `context.Context`，禁止在库代码中创建根 context |
| G-05 | 错误必须用 `fmt.Errorf("...: %w", err)` 包装保留错误链；对外只暴露领域错误码，不暴露底层错误 |
| G-06 | 禁止 `panic` 用于业务错误；仅在初始化阶段配置非法时 `panic` |
| G-07 | 禁止在事务内发起网络调用（数据库、对象存储、AI、邮件） |
| G-08 | 任何按 ID 查询单条资源的仓储方法必须显式接收 `userID` 并进入 SQL 条件 |
| G-09 | 时间获取统一使用 `platform/clock`，禁止业务代码直接 `time.Now()` |
| G-10 | 日志使用结构化字段，禁止字符串拼接；禁止记录密码、令牌、验证码、完整邮箱 |
| G-11 | 依赖方向遵守 [ARCHITECTURE.md](ARCHITECTURE.md) 5.2，`domain` 不得导入框架包 |
| G-12 | 新增依赖需在评审中说明理由与许可证，禁止引入 GPL/AGPL 依赖 |

### 3.2 分层落位

| 内容 | 允许落位 | 禁止落位 |
|---|---|---|
| HTTP 参数解析与校验 | `transport/http` | `application`、`domain` |
| 事务编排 | `application/usecase` | `transport`、`domain` |
| 业务不变量、状态迁移判断 | `domain/entity`、`domain/service` | `transport`、`infrastructure` |
| SQL | `infrastructure/postgres` | 其他任何位置 |
| 预签名与对象校验 | `infrastructure/objectstore` | `application`、`domain` |

### 3.3 测试

| 编号 | 规则 |
|---|---|
| T-01 | `domain` 与 `application` 必须有单元测试，用例名使用中文描述行为 |
| T-02 | 涉及事务、唯一索引、软删除、额度返还的路径必须有集成测试（真实 PostgreSQL） |
| T-03 | 越权用例、冲突用例、额度边界用例是**必测三件套**，新增资源类型时必须补齐 |
| T-04 | 禁止依赖执行顺序；测试数据必须自清理或使用独立事务回滚 |
| T-05 | 测试中不得访问真实 AI 供应商与真实邮件服务，使用适配器桩 |

| 对象 | 命名规则 | 示例 |
|---|---|---|
| 文件 | 小写下划线 | `conversion_job.go` |
| 领域实体 | 单数名词 | `Note`、`Folder` |

## 5. Git 规范

### 5.1 提交信息

遵循 Conventional Commits 1.0.0（出处：<https://www.conventionalcommits.org/zh-hans/v1.0.0/>）：

```text
<type>(<scope>): <subject>

<body>

<footer>
```

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化 |
| `test` | 测试 |
| `build` / `ci` | 构建与流水线 |
| `chore` | 杂项 |

规则：标题不超过 72 字符、使用中文陈述句、不以句号结尾；`scope` 使用包名或模块名（`auth`、`note`、`conversion`）；破坏性变更在 footer 写 `BREAKING CHANGE: 说明`。

### 5.2 分支

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 可发布基线，禁止直接推送 | 长期 |
| `feat/<topic>` | 功能开发 | 合并后删除 |
| `fix/<topic>` | 缺陷修复 | 合并后删除 |
| `docs/<topic>` | 文档 | 合并后删除 |

### 5.3 提交粒度

一次提交只做一件事；文档变更与代码变更尽量分开提交；禁止提交 `.env`、密钥、构建产物、本地数据目录（见 `.gitignore`）。

## 6. 文档写作规范

| 编号 | 规则 |
|---|---|
| D-01 | 每篇文档必须有「文档信息」表：编号、版本、状态、更新日期、适用范围、上级约束 |
| D-02 | 每篇文档必须有修订记录；版本号按 `v主.次`，结构性变更升主版本 |
| D-03 | 标题层级从 `##` 开始，一、二级标题必须编号，便于被注释以锚点引用 |
| D-04 | 规范用词固定为「必须 / 应当 / 可以 / 不得」，语义按 RFC 2119 |
| D-05 | 任何数值型约束必须标注出处（PRD 章节或标准链接），禁止无来源的魔法数字 |
| D-06 | 表格优先于长段落列举；流程与结构用 Mermaid 表达 |
| D-07 | 文档内引用其他文档使用相对链接，跨版本引用需注明版本号 |
| D-08 | 中英文之间加空格，代码、字段、路径用反引号包裹 |
| D-09 | 禁止在文档中粘贴大段代码作为规范；示例只用于说明格式 |

## 7. 评审清单（Definition of Done）

提交评审前逐项自查，任一项不满足则不得进入评审：

| 检查项 | 依据 |
|---|---|
| 无 `//` 注释（编译器指令除外） | C-01 |
| 每段代码前有块注释，且段落 ≤15 行 | C-02、C-03 |
| 注释解释意图与约束，未复述代码 | C-05 |
| 涉及的规则已在文档中定义，注释仅引用 | C-07、第 1 章 |
| 新增接口已同步 `API.md` 与 `openapi.yaml` | API.md 第 5、7 章 |
| 新增跨模块约束已写入架构文档第 8 章 | ARCHITECTURE.md |
| 越权、冲突、额度边界用例已覆盖 | T-03 |
| 无密钥、无 PII 进入日志与仓库 | G-10、5.3 |
| `gofmt`、`goimports`、lint 通过 | G-01 |
| 提交信息符合 Conventional Commits | 5.1 |

## 8. 规范的变更

本文档的修改必须走评审，并在修订记录中说明变更原因与影响范围。新增规则时不得与本文件既有编号冲突；废弃规则保留编号并标注「已废弃」，不得直接删除编号，以免历史注释中的引用失效。
